# Hisar Desktop

Wails v3 (pinned beta, see `WAILS_VERSION` in the root `Makefile`) with a Vue 3 + TypeScript frontend.

| Path | What |
|---|---|
| `vault/` | Go backend bound to the UI: session, lock/auto-lock, clipboard clearing, SSH Key items, sharing, invites, devices, account recovery and import. No Wails import, so it is tested on any OS |
| `agent/` | SSH agent in the app: approval window (Touch ID or in-app prompt, also for the command-line tool), `~/.ssh/config` setup, agent status. No Wails import |
| `commandline/` | The `hisar` CLI socket (`~/.hisar/cli.sock`): peer check, per-terminal-session approvals, and installing the bundled `hisar` on the PATH. No Wails import |
| `biometric/` | Touch ID and the macOS Keychain (cgo) |
| `updater/` | Sparkle bridge for automatic updates (cgo, build tag `sparkle`; packaged macOS builds only) |
| `main.go` | Wails app: window, clipboard, lock-event and approval-event adapters; starts the SSH agent |
| `frontend/src` | UI: `api.ts` (only file that calls the bindings), `store.ts` (state and actions), `components/` |
| `frontend/bindings` | Generated by `wails3 generate bindings` during every build; committed, and CI fails if a build changes them |
| `build/` | Platform build config (macOS, Linux) |

## Build and run on macOS

Requires Go 1.26+, Node 24 and Xcode command line tools.

```sh
make install-wails          # installs the pinned wails3 CLI into ~/go/bin
make package-desktop        # builds desktop/bin/Hisar.app (ad-hoc signed)
open desktop/bin/Hisar.app
```

For development with hot reload: `cd desktop && wails3 dev`.

### DMG and releases

`make package-desktop-dmg VERSION=0.1.0` builds a universal (Apple silicon and Intel) `Hisar.app` with Sparkle embedded,
sets its version, and writes `desktop/bin/Hisar-0.1.0.dmg` with the usual drag-to-Applications window
(`build/darwin/dmg-settings.py`, background rendered from `build/darwin/dmg-background.html`). It needs
`pip install dmgbuild==1.6.5`. Versions are `MAJOR.MINOR.PATCH` (each part up to 999); `CFBundleVersion` is the build number
`MAJOR × 1 000 000 + MINOR × 1 000 + PATCH` (`scripts/get-build-number.sh`), so Sparkle sees every release as newer.

`make package-desktop-update VERSION=0.1.0 SPARKLE_PRIVATE_KEY=<key file> [RELEASE_NOTES=<markdown file>]` also writes the
Sparkle update: `Hisar-0.1.0.zip`, signed with the EdDSA private key, and `update.json` (signature, length, minimum macOS,
release notes). The script refuses a key that does not belong to `SUPublicEDKey` in `build/darwin/Info.plist`.

Pushing an annotated tag `mac-v<version>` (e.g. `git tag -a mac-v0.1.0 -m "release notes in markdown"`) runs `desktop-dmg` on
the macOS runner, which builds both and uploads the DMG, the zip and `update.json` to the generic package registry
(`hisar-desktop/<version>`), and `desktop-release`, which creates a GitLab release with the DMG as a download. The tag
message becomes the release notes Sparkle shows. The job needs the protected File variable `SPARKLE_PRIVATE_KEY`. The app is
ad-hoc signed and not notarized until the Apple Developer membership is active, so the first launch needs right-click → Open
(or `xattr -dr com.apple.quarantine /Applications/Hisar.app`).

### Automatic updates

Design: `docs/DESIGN.md` §9.1.1. Sparkle (version and SHA-256 pinned in `scripts/download-sparkle.sh`, downloaded into
`build/sparkle/` by packaged builds) checks `<server>/api/v1/desktop/updates/appcast.xml` on the server you are signed in
to, with your session, once a day, and downloads the update from the same server. The server needs the update source
configured (`deploy/README.md`); otherwise checks report that updates are not configured. Settings → Updates shows the
version, **Check for updates**, and **Automatically check for updates**. `wails3 dev` builds have no Sparkle and say so.

The EdDSA private key lives outside the repository (kept by the maintainer and in the `SPARKLE_PRIVATE_KEY` CI variable);
losing it means existing installs can no longer verify updates, so keep a backup. Preview: `&settings=1&scroll=updates`,
`&updates=development` (build without Sparkle) or `&updates=signed-out`.

To work on the design without a server, run the UI in a browser with sample data:

```sh
cd desktop/frontend && npm run preview:ui
# http://127.0.0.1:5180/?state=signed-out | locked | unlocked
# extra parameters: &vault=family &item=netflix &editor=create|edit|ssh-key &secretKey=1 &search=git
# SSH: &item=raspberry (SSH key) &settings=1 &approval=1 (in-app approval prompt) &agent=error &sshConfigured=1
# sharing: &sharing=1 (sharing panel; add &vault=work for the read-only view) &code=elif (security code) &remove=deniz
# settings: &settings=1 &invite=form|1 (invite form, or a created link) &revoke=mac-mini &scroll=family|recovery|devices
# recovery (admin): &settings=1&scroll=recovery, plus &recovery=off&setUpRecovery=1 (setup confirmation), &recovery=other (set up by
#   another admin), &startRecovery=deniz (created link; use &scroll=family), &completeRecovery=deniz | &completedRecovery=deniz
# recovery (member): &settings=1&scroll=recovery&role=member &optOut=1 (personal vault opted out)
# personal vault: &vaultRecovery=1 (recovery panel) &disableRecovery=1 (opt-out warning) &optOut=1
# recovering an account: &state=signed-out&recover=form|filled &secretKey=recovery (new Secret Key) &recoverySubmitted=1
# offline: &offline=1 (offline notice)
# import: &import=choose | preview | saving (stops halfway) | done | deleted, &importVault=family (target vault), &newItemMenu=1 (open the + menu)
```

The preview backend (`src/preview.ts`) is loaded with a dynamic import behind a build-time flag; `npm run check:bundle` (run in CI) fails if it ever ends up in the production bundle.

The app keeps its session in `~/Library/Application Support/hisar/desktop.json` (override with `HISAR_DESKTOP_STATE`), the encrypted offline cache in `desktop-cache.db` next to it (override with `HISAR_DESKTOP_CACHE`), and the Secret Key in the macOS Keychain under the service `hisar`.

## Sharing, family and devices

Design: `docs/DESIGN.md` §4.4 (vault keys and rotation), §5.1 (invites) and §5.6 (public key pinning).

- **Share a vault**: select a shared vault and press **Share** in the item list header. Everyone with access is listed with their role; owners can add a family member (owner, editor or reader), change roles and remove people. Editors and readers see the list read-only. Personal vaults show **Private** instead and cannot be shared.
- **Removing someone** re-encrypts the vault: the owner's device generates a new vault key, re-encrypts every item and wraps the new key only for the remaining members (`session.RemoveVaultMember`). Copies the removed person already downloaded stay readable to them.
- **Key pinning**: the first time this device shares with someone, it pins their signing key in `desktop.json` (`pins`), like the CLI (`localstate.State.CheckMemberPin`). Sharing, changing a role or re-encrypting the vault stops if a pinned key changes. Each person has a security code (`crypt.FormatKeyFingerprint`: the first 8 bytes of SHA-256 of their Ed25519 signing key, as 4 groups of 4 hex digits); expand a member in the sharing panel or open Settings → Family to see it, and compare it in person.
- **Settings → Family** lists everyone on the server with their role and security code. Admins can **Invite someone**: the link is valid for 7 days and works once.
- **Settings → Devices** lists the devices signed in to your account. **Revoke** signs another device out; to sign out this Mac, use **Sign out** under Account.

## Account recovery

Design: `docs/DESIGN.md` §6. Recovery lets an admin help someone who forgot their master password or lost their Secret Key; the trade-off is that the admin's devices can open every recoverable vault.

- **Set up (admin)**: Settings → Account recovery → **Set up** creates the recovery key and makes the vaults you own recoverable. Only the admin who set it up can complete recoveries. Settings also lists your own vaults with their state, and **Make recoverable** fixes vaults created before recovery was set up.
- **Start (admin)**: Settings → Family → **Start recovery** on someone's row creates a one-time link, valid for 7 days. Send it to them; their account keeps working until you complete the recovery.
- **Recover (the person who lost access)**: on the sign-in screen, **Recover account**, then paste the link, enter the email and a new master password. Hisar shows the new Secret Key (and can save it as an Emergency Kit); it works once the admin completes the recovery.
- **Complete (the admin who set up recovery)**: Settings → Account recovery lists pending recoveries with how many of their vaults can be recovered. **Complete** signs out their devices, gives them their recoverable vaults under the new keys, re-pins their new signing key on this device and lists the vaults they lost.
- **Opt out**: the owner of a personal vault can press **Private** in its header and turn recovery off, after a warning that the vault is lost if they lose access, and turn it back on later. Shared vaults always stay recoverable.

## Import from other password managers

Settings → Import → **Import…**, or **+** → **Import…** in a vault. The parsing is `core/importer` (design: `docs/DESIGN.md` §9.7).

1. Choose the vault (only vaults you can edit) and the format, or let Hisar detect it, then pick the file in the open dialog: a 1Password `.1pux` or CSV export, an unencrypted Bitwarden `.json` or CSV export, or a CSV export from Chrome, Edge, Firefox, Safari or another manager (header row with columns such as title, username, password, url, notes).
2. The preview counts logins, secure notes and SSH keys, lists what is not imported and why (cards, identities, documents, archived items, passphrase-protected SSH keys), and lists items already in the vault with the same title, username and website, which are skipped unless you untick the box. Nothing is saved before **Import**.
3. Items are saved in batches of 10 with a progress bar; if the connection drops, **Try again** continues where it stopped. Locking Hisar discards the parsed file.
4. The export holds every password in plain text, so Hisar offers to delete it (**Delete file** removes it directly, not through the Trash).

## Browser extension bridge

The Hisar extension (`extension/`) fills and saves logins through the desktop app (design: `docs/DESIGN.md` §9.2).

- `Hisar.app/Contents/MacOS/hisar-browser-host` is the native messaging host. At launch the app writes `com.tryhisar.hisar.json` into `NativeMessagingHosts` of every installed Chromium browser (Chrome, Chrome Beta/Canary, Chromium, Brave, Edge, Arc, Vivaldi), allowing only the extension `mmipiffoogblblocokimpemdopmdjghf`. Settings → Browser extension shows where it is registered. A development build (`wails3 dev`) has no host next to its binary and registers nothing.
- The host relays to the app on `~/.hisar/browser.sock` (`HISAR_BROWSER_SOCKET` overrides it for both). In the packaged app only that host binary may connect. If the app is not running, the host opens it in the background.
- Pairing: clicking the extension's icon the first time makes Hisar show a 6-digit code (2 minutes, 5 attempts) to type into the extension. Settings → Browser extension lists paired browsers with Remove and has "Only fill on the exact host".
- Preview: `&settings=1&scroll=browser-extension` (registered and paired browsers), `&browsers=none` (nothing found), `&browserPairing=1` (pairing code).

## SSH agent

Hisar is an SSH agent for the SSH keys in your vaults (design: `docs/DESIGN.md` §9.6).

1. Add a key: **+** → **SSH key**, then **Generate** (Ed25519, or RSA 4096 for old servers) or **Import** (paste an OpenSSH or PEM private key; a passphrase is only needed to import, the key is stored without it).
2. Copy the public key from the key's page (**Copy public key**) into GitHub or the server's `~/.ssh/authorized_keys`.
3. Settings → SSH agent → **Use Hisar for SSH**. This backs up `~/.ssh/config` to `~/.ssh/config.hisar-backup-<timestamp>` and adds at the top:

   ```
   # Added by Hisar: use the Hisar SSH agent
   Host *
     IdentityAgent "~/.hisar/agent.sock"
   # End of Hisar section
   ```

   **Remove from SSH config** takes the section out again. To try it without changing the config: `SSH_AUTH_SOCK=~/.hisar/agent.sock ssh-add -l`.

The agent listens on `~/.hisar/agent.sock` while the app runs (`HISAR_SSH_AGENT_SOCKET` overrides the path) and offers keys from all your vaults only while Hisar is unlocked. The first time a program (`ssh`, `git`, …) uses a key, Hisar opens its approval window ("Hisar Access Requested", with the app the program runs in); Authorize then asks for Touch ID on Macs that have it. Unanswered requests are denied after 60 seconds. Preview: `?window=ssh-approval&approval=1` (or `=2` for two waiting, `&forwarded=1`, `&noTouchID=1`). Approvals last for an hour, or until Hisar locks.

## Command-line tool

Design: `docs/DESIGN.md` §9.4. The packaged app bundles the CLI as `Hisar.app/Contents/Helpers/hisar` (universal, signed with the
app, updated with it by Sparkle). Not `Contents/MacOS/hisar`: on the default case-insensitive file system that is the app's own `Hisar`.

- Settings → Command-line tool → **Install command-line tool** links `hisar` into `/opt/homebrew/bin` or `/usr/local/bin` (whichever
  exists and is writable first), else `~/.local/bin`, without an administrator password; Settings then shows a one-line PATH hint
  if that directory is not on your `PATH`. It never replaces a `hisar` that is not a link into a `Hisar.app`. **Uninstall** removes only such links.
- **Let the command-line tool use Hisar** (on by default) serves `~/.hisar/cli.sock` (`HISAR_CLI_SOCKET` overrides it for the app and
  `hisar`). `hisar` then runs its commands through the app: the first command in a terminal opens the approval window ("hisar in Terminal
  wants to use Hisar") with Touch ID, which also unlocks a locked Hisar (or asks for the master password). The approval lasts until 10
  minutes after that terminal's last command, or until Hisar locks or quits. `hisar status` shows which mode it uses.
- Without the app (not running, switch off), or with `hisar --standalone` / `HISAR_STANDALONE=1`, `hisar` signs in on its own as before.
- Preview: `&settings=1&scroll=command-line` plus `&commandLine=not-installed | conflict | path-hint | development | off`;
  the approval window with `?window=ssh-approval&approval=cli` (add `&cliLocked=1` for Touch ID unlock, `&cliPassword=1` for the
  master password, which is `correct horse battery` in the preview).
